# 문서 작성 안내

새 문서를 작성하기 전에 독자와 목적을 정하십시오. 같은 설명이 이미 있다면 새 파일을 만들지 말고 기존 원본을 수정하십시오.

## 문서 종류 선택

| 필요한 설명 | 폴더 | 들어갈 내용 |
|---|---|---|
| 처음 따라 해보는 일 | `{{human}}/tutorials/` | 준비물, 작은 목표, 실행 순서, 성공 결과 |
| 알고 있는 작업의 방법 | `{{human}}/how-to/` | 적용 조건, 작업 순서, 결과 확인, 복구 방법 |
| 동작 원리와 설계 이유 | `{{human}}/explanation/` | 개념, 배경, 선택한 이유, 다른 방법과의 차이 |
| 정확한 값과 규칙 | `{{human}}/reference/` | 정의, 필드·명령 표, 예제, 제한 |
| AI가 작업할 때 지킬 내용 | `{{ai}}/` 또는 `AGENTS.md` | 작업 범위, 읽을 파일, 검사 명령 |
| 과거 보고서와 초안 | `{{human}}/archive/` | 작성 당시의 날짜·목적, 현재 문서와의 관계 |

영역이 여러 개이면 종류 폴더 아래에 영역 폴더를 추가하십시오. 예시는 `{{human}}/how-to/deploy/`입니다.

## 파일 위치 결정

먼저 [원본 문서 위치](../reference/document-locations.md)를 확인하십시오. API·빌드·설정과 함께 바뀌는 설명은 해당 코드와 같은 저장소에 작성합니다. 여러 팀이 함께 보는 규칙과 배경 설명은 공통 문서에 작성합니다.

사람용 문서와 AI용 문서는 읽는 목적이 다릅니다. 같은 제품 규칙을 양쪽에 복사하면 두 문서를 따로 관리해야 합니다. AI용 문서는 사람용 원본 문서로 연결하십시오.

## 말투와 구성

설명 문장은 `~입니다.`, 실행을 안내하는 문장은 `~하십시오.`가 기준입니다. 한 문장에는 한 가지 내용만 적으십시오. 표와 체크리스트는 짧은 항목 형식입니다.

긴 대시로 설명을 덧붙이지 마십시오. 조건·이유·예외는 다음 문장이나 별도 항목으로 나누십시오. 런북은 짧은 소개, 확인 순서, 증상별 조치 표로 구성합니다.

### 제목·표·용어 규칙

- 제목은 명사형입니다. `~한다`, `~않는다`, `~인가`, `~않게`로 끝나는 문장·질문형 제목은 쓰지 마십시오.
- 표 칸과 목록 항목은 `~함`, `~음`, `~ 여부`나 명사구로 끝냅니다. `~다`로 끝나는 문장은 본문에만 씁니다.
- 대화체와 비유 대신 기술 용어를 쓰십시오. 코드와 서버를 사람처럼 표현하지 마십시오.
- 정보를 더하지 않는 강조·요약 문장은 지우십시오.
- 이 규칙은 문서뿐 아니라 커밋 메시지, PR, 코드 주석에도 적용합니다.

| 피할 표현 | 고친 표현 |
|---|---|
| 다섯 가지 상태를 나눠 준다 (제목) | 응답 상태 |
| 아직 답이 없다 (표 칸) | 아직 응답을 받지 못함 |
| 서버가 넘어졌다 | 서버 오류 |
| 이 5개가 전부입니다 | (삭제) |

devdog 플러그인을 설치했다면 `kolint.py`로 문체 규칙을 검사할 수 있습니다.

첫 문단에는 문서가 설명하는 내용을 적으십시오. 문서 1개에는 제목 1개와 주제 1개만 작성합니다. 긴 배경 설명은 별도 개념 문서로 분리해 연결하십시오.

작업 절차 문서의 템플릿은 다음과 같습니다.

````markdown
# 작업 이름

이 문서는 [독자]가 [환경]에서 [목표]를 달성하는 데 필요한 안내입니다.

## 준비

- 필요한 도구와 권한
- 적용할 환경

## 순서

1. 첫 번째 작업
2. 두 번째 작업

```bash
실제로_확인한_명령
```

## 결과 확인

- 성공했을 때의 응답이나 화면
- 실패했을 때 확인할 파일과 로그

## 관련 자료

- 근거가 되는 코드·설정
- 확인한 버전이나 커밋
- 이 문서를 함께 고쳐야 하는 변경
````

확인한 사실, 아직 확인하지 않은 내용, 제안은 구분해 작성하십시오. 명령을 실행할 디렉터리와 확인한 버전도 함께 적으십시오. 비밀값은 문서에 넣지 마십시오. 이미지 설명과 내용을 알 수 있는 링크 이름은 항상 작성하십시오.

## 링크와 목록 확인

같은 저장소 안에서는 상대 링크를 사용하십시오. 다른 저장소의 자료는 GitHub 원본 링크로 연결하고, AI가 찾을 로컬 경로는 [AI 참고 파일 목록](../../ai/sources.json)에 추가하십시오. 파일을 이동하면 관련 링크, 폴더 README, 참고 파일 목록을 함께 수정하십시오.

`docs.config.json`이 있는 저장소 루트에서 다음 명령을 실행하십시오.

```bash
python3 scripts/check_docs.py --write-catalog
python3 scripts/check_docs.py
```

문서 허브 구조에서는 형제 저장소까지 함께 검사합니다.

```bash
python3 scripts/check_docs.py --workspace
```

검사 대상은 문서 경로와 링크, 제목 단계, 코드 블록의 언어, 이미지 설명, 파일 목록입니다. 인터넷 주소의 접속 여부와 문서에 적힌 명령의 실제 결과는 별도로 확인하십시오.

## 문서 갱신 기준

기능을 새로 만들거나 기존 동작을 바꾸는 작업에는 관련 문서 갱신까지 포함입니다. AI도 별도 요청을 기다리지 말고 같은 작업에서 문서를 고치십시오. 구현과 문서가 일치해야 작업 완료입니다.

### 변경에 따라 고칠 문서

| 바뀐 내용 | 함께 확인할 문서 |
|---|---|
| API 요청·응답·오류·권한 | API 원본, 연동 안내, 관련 예제 |
| 화면·사용 흐름·로딩·오류 처리 | 화면 설명, 사용 방법, 필요 시 런북 |
| 도메인 규칙·DB 구조·마이그레이션 | 도메인 설명, 데이터 문서, 적용 절차 |
| 환경변수·실행 명령·빌드·배포 | 설정 목록, 로컬 실행 안내, 배포 절차 |
| 운영 동작·장애 대응·복구 | 런북, 관측·복구 절차 |
| 파일 위치·작업 순서·검사 명령 | 관련 README, `AGENTS.md`, AI 참고 파일 목록 |

모든 변경에 새 문서가 필요하지는 않습니다. 먼저 원본 문서 위치를 확인하고 기존 설명을 수정하십시오. 새 파일은 설명할 내용이 기존 문서에 맞지 않을 때만 추가하십시오.

### AI 작업 완료 전 확인

1. 바뀐 기능과 관련된 사람용 원본 문서를 갱신하십시오.
2. AI가 참고할 경로·명령·규칙이 바뀌었다면 해당 저장소의 `AGENTS.md`, AI용 문서, 참고 파일 목록을 갱신하십시오. 제품 설명은 원본 문서로 연결하십시오.
3. 파일 추가·이동 시 관련 README와 링크를 고치고 `catalog.json`을 재생성하십시오.
4. 위의 문서 검사 명령을 실행하고 오류를 고치십시오. 문서 허브 구조에서는 `--workspace` 검사도 완료 조건입니다.
5. 완료 보고에는 갱신한 문서와 검사 결과를 포함하십시오. 문서 변경이 필요 없다면 이유를 적으십시오. 실행하지 못한 검사는 실행한 결과와 구분하십시오.

문서를 갱신하지 않은 상태를 전체 작업 완료로 보고하지 마십시오. 폐기한 규칙과 날짜가 있는 비교 보고서는 `archive/`에 보관합니다.
